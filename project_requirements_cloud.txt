PROJECT REQUIREMENTS — CLOUD INFRASTRUCTURE SIMULATION
==============================================================

Title:
Secure, Reliable & Scalable Cloud Infrastructure Simulation for an AI Healthcare Platform

Assessment:
DevSecOps, Cloud Engineering, Infrastructure, Reliability & Operations Assessment

Product Owner: AI.Prof
Version: 2.0
Target Duration: 3–4 Days
Implementation Scope: Infrastructure and operations simulation

IMPORTANT SCOPE
---------------
- Application development is NOT required.
- Real cloud deployment is NOT required.
- The healthcare application may be simulated.
- The assessment focuses on infrastructure and operational engineering.

1. PROJECT OVERVIEW
-------------------
Evaluate the ability to design, secure, automate, operate, monitor, troubleshoot, and recover
a production-style cloud environment for an AI-powered healthcare platform.

The simulated application consists of:
- API
- AI/Agent service
- Background worker
- Database
- Queue
- Scheduling/integration workflows
- External healthcare system

The infrastructure must demonstrate:
- Controlled traffic entry
- Public/private service boundaries
- Secure service communication
- Secret protection
- Reproducible infrastructure
- Safe development-to-production deployment
- Failure detection and recovery
- Scaling
- Rollback
- Security failures blocking unsafe releases

A real cloud account is not required. The focus is engineering decisions and operational behavior.

2. PROJECT PHILOSOPHY
---------------------
The final system should behave like a small production cloud environment even if it runs locally.

Important concepts:
- Networking
- Compute/containers
- Infrastructure as Code
- Deployment automation
- Security controls
- Monitoring
- Logging
- Alerting
- Failure recovery
- Scaling

Technology choices are open. Explain why each significant technology was selected and its trade-offs.

3. SIMULATED HEALTHCARE PLATFORM
--------------------------------
PATIENT/API SERVICE
- Internet-facing entry point.
- Controlled ingress.
- Health checks.
- Secure communication.
- Horizontal scaling.
- Must not expose internal infrastructure directly.

AI/AGENT SERVICE
- Internal service.
- Controlled internal communication.
- Controlled external AI access where applicable.
- Actual AI agent is NOT required; a mock is sufficient.
- Demonstrate secrets, resource controls, isolation, and monitoring.

BACKGROUND WORKER
- Represents asynchronous processing.
- Examples: appointment processing, notifications, EHR synchronization.
- Must allow observation of:
  - Queue depth
  - Processing latency
  - Failed jobs
  - Retry behavior
  - Worker health
  - Worker restarts
- Worker failure and recovery must be demonstrable.

DATABASE
- Relational database representing application state.
- Complete healthcare data model is NOT required.
- Must be private.
- Must not be directly accessible from the public internet.

EXTERNAL EHR / HEALTHCARE SYSTEM
- Mock external service.
- Must support:
  - Success
  - Slow responses
  - Timeouts
  - Temporary failures
  - Authentication failures
  - Unavailable service
  - Unknown operation outcome

QUEUE / BACKGROUND PROCESSING
- Connect asynchronous workloads.
- Must support:
  - Normal workload
  - Increased workload
  - Queue growth
  - Worker failure
  - Worker recovery
  - Retry behavior

Architecture should contain:
- Controlled public entry point
- Public-facing API access
- Private internal services
- Background workers and queue
- Private database
- Controlled external-system communication
- Monitoring and security boundaries

5. SIMULATION ENVIRONMENT
-------------------------
The project must run in a controlled environment.

Allowed approaches include:
- Local containers
- Infrastructure simulators
- Local orchestration
- Simulated cloud resources
- Local networking
- Mock external services

Evaluator should be able to:
1. Start the environment
2. Inspect infrastructure
3. Generate workload
4. Deploy changes
5. Introduce failures
6. Observe behavior
7. Recover the system

Architecture should conceptually transition to real cloud with minimal redesign.

6. INFRASTRUCTURE AS CODE
-------------------------
Infrastructure must be represented as code. Manual infrastructure creation must not be primary.

IaC should cover:
- Networking
- Compute/containers
- Load balancing/ingress
- Security controls
- Database
- Queues
- Monitoring
- Secrets/configuration
- Environment configuration

Infrastructure must be:
- Reproducible
- Version controlled
- Parameterized
- Repeatable
- Environment aware
- Destroyable
- Re-creatable

Development and production-like environments should reuse infrastructure definitions where possible.

7. ENVIRONMENT MANAGEMENT
-------------------------
Provide at least:
- Development
- Production-like

They should be separated while sharing reusable infrastructure definitions.

Environment-specific values must not require copying the entire infrastructure implementation.

8. NETWORK ARCHITECTURE
----------------------
Clearly separate public and private resources.

Public:
- Controlled ingress/API entry point

Private:
- Database
- Workers
- Queues
- Internal services
- Management interfaces where applicable

Requirements:
- No unnecessary internet exposure
- Controlled inbound traffic
- Controlled outbound traffic
- Restricted administrative access
- Document trust boundaries and reasons for public/private placement

9. SECURITY ARCHITECTURE
------------------------
Security must be built throughout the infrastructure.

Network security:
- Restrict inbound traffic
- Minimize exposed ports
- Isolate internal services
- Protect database
- Restrict administration
- Control outbound traffic where appropriate

Identity and access:
- Use least privilege.
- Separate developer, deployment, runtime, database, monitoring, and infrastructure permissions where appropriate.
- Avoid unrestricted privileges.

Secrets:
- NEVER hard-code secrets in:
  - Source code
  - Container images
  - IaC
  - Public configuration
  - Version control
- Applies to DB, API, service, external integration, and AI provider credentials.
- Explain secure storage and injection into workloads.

10. CONTAINER & RUNTIME SECURITY
-------------------------------
Where containers are used:
- Keep images minimal.
- Avoid unnecessary packages.
- Run as non-root where practical.
- Validate dependencies for known vulnerabilities.
- Avoid unnecessary privileges and unsafe runtime settings.
- Use isolation, permissions, network controls, and controlled secret access.

Include a mechanism for identifying container vulnerabilities.

11. INFRASTRUCTURE SECURITY VALIDATION
--------------------------------------
Security checks should identify:
- Public exposure of private resources
- Overly permissive access
- Dangerous network rules
- Hard-coded secrets
- Insecure infrastructure configuration
- Weak container configuration
- Vulnerable dependencies/images

Security validation must produce actionable results and be integrated into engineering workflow.

12. DEVSECOPS CI/CD PIPELINE
----------------------------
Provide a simulated CI/CD pipeline containing major safe-release stages.

Recommended stages:
1. Validation
2. Testing
3. Security checks
4. Infrastructure validation
5. Container/artifact creation
6. Artifact validation
7. Deployment
8. Health verification
9. Success or rollback

Security must be integrated into the pipeline, not only manually reviewed at the end.

Security checks may include:
- Source/dependency scanning
- Container image scanning
- Infrastructure security validation
- Secret detection
- Configuration validation

At least ONE meaningful security failure must be demonstrated.
A failed security check must be able to prevent unsafe deployment.

13. DEPLOYMENT & RELEASE SAFETY
-------------------------------
Deployments must be versioned and controlled.

Healthy release flow:
1. Deploy new version.
2. New version becomes ready.
3. Verify health.
4. Shift traffic in a controlled manner.
5. Remove old version only after health is confirmed.

Failed release flow:
- New version fails health verification.
- Previous healthy version remains available.
- Rollout stops.
- System recovers or rolls back.

Demonstrate zero-downtime-style controlled behavior.

14. RELIABILITY, HIGH AVAILABILITY & RESILIENCE
-----------------------------------------------
Consider:
- API failure
- Worker failure
- Container/instance failure
- External EHR failure
- Queue backlog
- Database connectivity failure
- Deployment failure
- Configuration failure

Avoid unnecessary single points of failure.

Possible mechanisms:
- Multiple instances
- Health checks
- Load distribution
- Automatic restart/replacement
- Failure isolation
- Retry mechanisms
- Dependency-aware recovery

Multi-region deployment is NOT required.

15. SCALABILITY & PERFORMANCE
-----------------------------
Architecture should scale without fundamental redesign.

- API and worker capacity should be independently scalable.
- Demonstrate increased workload.
- Measure meaningful characteristics:
  - API latency
  - Startup time
  - Worker processing time
  - Queue latency
  - Database connectivity
  - Network latency
  - Resource utilization
  - Deployment duration where applicable
- Identify bottlenecks and explain how they are addressed.

16. OBSERVABILITY
-----------------
Operators should understand system state without manually inspecting every component.

LOGGING
- Application logs
- Infrastructure logs
- Worker logs
- Deployment logs
- Security-related events
- Include enough context for troubleshooting.

METRICS
At minimum:
- Request rate
- Error rate
- Latency
- CPU
- Memory
- Queue depth
- Worker processing rate
- Worker restarts
- Deployment state
- Service availability

HEALTH CHECKS
- Services should expose useful health/readiness information.
- Use health checks for deployment validation and monitoring.

OPERATIONAL DASHBOARD
Should show:
- API health
- Worker processing
- Queue growth
- Database reachability
- Deployment health
- External dependency failures
- Resource saturation

17. ALERTING
------------
Alerts should be actionable.

Consider alerts for:
- API unavailable
- High error rate
- Excessive latency
- Worker failure
- Queue backlog
- Database unavailable
- Deployment failure
- Resource exhaustion
- Security validation failure

Document why each alert matters and the operator action.

18. INCIDENT SIMULATION & RESPONSE
----------------------------------
Intentionally introduce at least TWO meaningful infrastructure/operational failures.

Examples:
- API failure
- Worker backlog
- External EHR outage
- Failed deployment
- Database connectivity failure

Demonstrate:
Failure → Detection → Investigation → Root Cause → Recovery → Verification → Prevention

At least ONE incident must be documented in detail with:
- What failed
- Impact
- Detection
- Root cause
- Recovery
- Evidence
- Prevention

19. BACKUP, RECOVERY & DISASTER CONSIDERATIONS
----------------------------------------------
Address:
- Database backup/recovery
- Infrastructure recreation
- Configuration recovery
- Persistence of important state

Explain:
- What happens if database/stateful infrastructure is lost.
- Recovery objectives.
- Difference between recreating infrastructure and recovering persistent state.

Full enterprise disaster recovery is NOT required.

20. INFRASTRUCTURE RESILIENCE & FAILURE ANALYSIS
-----------------------------------------------
Identify possible single points of failure across:
- API
- Workers
- Queue
- Database
- External healthcare system
- Deployment system
- Monitoring

For important dependencies, explain:
- What happens when unavailable
- Impact
- Reasonable trade-offs

21. OPERATIONAL ACCESS & AUDITABILITY
-------------------------------------
Distinguish where appropriate:
- Developer access
- Deployment access
- Infrastructure administration
- Runtime permissions
- Monitoring access

Avoid unrestricted administrative privileges.

Reviewer should be able to determine:
- Who initiated deployment
- Version deployed
- Infrastructure changes
- Security checks run
- Deployment success/failure
- Incident time
- Recovery action

22. COST AWARENESS
------------------
Identify:
- Potentially expensive resources
- Dynamically scalable resources
- Resources that can remain minimal
- Overprovisioning risks

Explain trade-offs between:
- Reliability
- Performance
- Security
- Cost

23. REQUIRED SIMULATION SCENARIOS
---------------------------------
NORMAL OPERATION
- Start infrastructure.
- Demonstrate API, internal services, worker, queue, database, external dependency.
- Show logs, metrics, health checks, dashboard.

INCREASED WORKLOAD
- Generate additional API/background workload.
- Show queue growth, worker processing, latency, resource use, and scaling where implemented.

WORKER FAILURE
- Stop/break worker.
- Show queue behavior.
- Detect failure.
- Recover worker.
- Show processing resumes.

EXTERNAL DEPENDENCY FAILURE
- Make EHR slow/unavailable/failing.
- Demonstrate timeout, retry, failure handling, monitoring, recovery.

DEPLOYMENT
- Deploy healthy new version.
- Demonstrate controlled rollout and health verification.

FAILED DEPLOYMENT
- Deploy deliberately unhealthy version.
- Detect problem.
- Prevent/reverse unsafe release.
- Preserve service availability where possible.

INFRASTRUCTURE RECOVERY
- Destroy/restart important component.
- Demonstrate recovery/recreation.

Scenarios must be repeatable for evaluator verification.

28. EXPECTED ENGINEERING THINKING
---------------------------------
Architecture:
- Why is database private?
- Why is API public?
- Where are trust boundaries?
- How do internal services communicate?

Security:
- What happens if a container is compromised?
- How are credentials protected?
- What permissions does each workload require?
- How are insecure configurations detected?

Reliability:
- What happens when API dies?
- What happens when worker stops?
- What happens when queue grows?
- What happens when EHR is unavailable?

Deployment:
- How is release health determined?
- What happens when unhealthy?
- How is healthy version protected?

Observability:
- How does operator know something is failing?
- How is affected component identified?
- What evidence supports root cause?

Scalability:
- Which components scale independently?
- What happens as workload increases?
- What are likely bottlenecks?

Strong submissions demonstrate these decisions through implementation AND explanation.

32. FINAL DEMONSTRATION STORY
----------------------------
1. Start environment and show normal operation.
2. Show architecture and network boundaries.
3. Show infrastructure and recreation.
4. Run CI/CD and security validation.
5. Deploy healthy version and verify health.
6. Introduce meaningful failure.
7. Demonstrate detection, alerting, investigation, and recovery.
8. Deploy intentionally broken version.
9. Demonstrate health validation preventing/reversing unsafe release.
10. Explain security, reliability, scalability, cost, and architecture trade-offs.

Evaluator may ask for modifications or troubleshooting during demonstration.
Understand the implementation; do not rely only on pre-recorded output.

34. FINAL PROJECT DEFINITION
----------------------------
A secure, reliable, observable and scalable cloud infrastructure simulation for a modern
AI-powered healthcare platform.
